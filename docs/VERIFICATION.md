# Verification and reproducibility checklist

This page separates checks that can be run immediately from experiments that need
external data, checkpoints, or a CUDA GPU.

## 1. Verify the published records

Run these commands from the repository root:

```bash
python tools/verify_release_records.py
python tools/verify_completion_records.py
python tools/verify_completion_records.py --check-arrays
python tools/paired_statistics.py
```

The expected record counts are:

| Check | Expected result |
|---|---:|
| Published files | 275 |
| Eval1 FPGA runs | 40 |
| GPU power trials | 42 |
| GPU power settings | 14 |
| FP32 reports in the completion archive | 28 |
| FP32 summary rows | 112 |
| D1 full-scene tiles | 858 |
| D1 source files | 10 |
| DT diagnostic rows | 18 |

These checks use the files already in `evidence/`; they do not download datasets
or checkpoints and they do not run model inference.

## 2. Run the software tests

After installing the environment described in [`ENVIRONMENT.md`](ENVIRONMENT.md):

```bash
python -m unittest discover -s tests -v
cd software
python -m unittest discover -s tests -v
```

The first command checks release records and launcher behavior. The second checks
rounding, saturation, D-path behavior, initialization, device dispatch, fixed
GPU arithmetic, and simulation recovery. The tests use synthetic fixtures and do
not replace a full four-dataset run.

## 3. Validate the command planners

Every numbered launcher supports `--dry-run`. For example:

```bash
bash experiments/01_fp32_current.sh --dry-run
bash experiments/13_qat_eval1.sh --dry-run
bash experiments/14_fpga_eval1.sh --dry-run
bash experiments/11_gpu_fp32.sh --dry-run
bash experiments/12_gpu_fixed.sh --dry-run
bash experiments/16_gpu_power.sh --allow-display-processes --dry-run
```

The dry-run output shows the resolved dataset, seed, checkpoint template, device,
and output directory. It must not create a result directory or start a child
process. Use a fresh output directory for every real run.

## 4. What can be reproduced from the repository

| Result | Required inputs | Reproduction entry |
|---|---|---|
| Hashes and bundled summaries | Repository only | `tools/verify_release_records.py` |
| Stored D1 replay arrays | Repository only | `tools/verify_completion_records.py --check-arrays` |
| FP32 training and preprocessing | Four raw scenes + Linux/CUDA environment | `experiments/01_fp32_current.sh` |
| Batch=1 QAT | FP32 outputs + four scenes + CUDA | `experiments/13_qat_eval1.sh` |
| FPGA fixed-point simulation | QAT checkpoints + FP32 outputs + four scenes + CUDA/CPU reference | `experiments/14_fpga_eval1.sh` |
| GPU timing | Matching checkpoint + CUDA GPU | `experiments/11_gpu_fp32.sh`, `experiments/12_gpu_fixed.sh` |
| GPU power | Matching checkpoint + NVML-capable GPU | `experiments/16_gpu_power.sh` |
| RTL resource/timing/board result | Separate RTL/Vivado project and board | Not generated by this repository |

## 5. External files that must be supplied

Place the four raw datasets according to [`DATA.md`](DATA.md). The FP32 and QAT
stages also require their generated preprocessing files and checkpoints. These
large or license-restricted files are intentionally not part of the source
repository; set `DATA_ROOT`, `FP32_ROOT`, and `QAT_ROOT` to their locations before
running the corresponding launcher.

The software simulator can reproduce the numerical semantics and labels of the
published fixed-point path. It does not create an FPGA bitstream, Vivado timing
report, post-route power estimate, or board measurement. Those outputs require
the separate RTL project and target board.
